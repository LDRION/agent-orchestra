# Безопасность

## Угрозы и защита

| Угроза | Защита | Где |
|---|---|---|
| Утечка проектных данных в облачную модель | Гриф задачи и агента × уровень доверия провайдера; облако — только с правом `providers.external` или по визе; маскирование ПДн | `providers/egress.py`, `providers/service.py` |
| Агент делает то, чего нельзя человеку («запутанный заместитель») | Права шага = права инициатора ∩ инструменты агента; виза действует на одну задачу | `orchestration/engine.py` |
| Промпт-инъекция из документов и результатов шагов | Данные в тегах «это данные, не инструкции»; план проверяется кодом (только известные агенты, граф без циклов); инструменты — по белому списку и правам | `orchestration/planner.py`, `executor.py` |
| Кража ключей API | AES-256-GCM, привязка шифротекста к записи (AAD), мастер-ключ вне БД (DPAPI / docker secret); ключ не возвращается в интерфейс и не пишется в журналы | `core/crypto.py`, `core/redact.py` |
| Перебор паролей | Argon2id; блокировка после 5 ошибок; лимиты по IP (IPv6 — по сети /64) и по логину считают только неудачи — офис за одним NAT входит без помех; одинаковые ответ, код (429) и время для «нет логина», «неверный пароль» и «заблокирован»; тревога администраторам | `iam/service.py`, `api/auth.py`, `core/ratelimit.py` |
| Перебор пароля из украденной сессии | Повторная проверка пароля (подтверждение действия, смена пароля, отключение 2FA): после 6 ошибок сессия закрывается и поднимается тревога | `api/auth.py` |
| Украденный пароль | Второй фактор TOTP (RFC 6238): каждый код — один раз, коды восстановления хранятся хешами; верный пароль не сбрасывает счётчик ошибок, пока не введён код; на сервере 2FA обязателен для управляющих доступами и моделями — без него открыт только раздел входа | `core/totp.py`, `iam/mfa.py`, `iam/deps.py` |
| Утечка документов через поиск агента | Агент видит только документы, доступные инициатору, и только с грифом не выше грифа шага | `knowledge/service.py`, `knowledge/tool.py` |
| Вредоносные файлы в базу знаний | Белый список форматов, 15 МБ, проверка распаковки .docx, лимит страниц PDF, разбор в отдельном потоке с таймаутом; тело без Content-Length отклоняется | `knowledge/ingest.py`, `app.py` |
| Перерасход денег на облачные модели | Дневной лимит токенов на человека и на модель; исчерпан лимит модели — следующая в цепочке | `providers/service.py` |
| Агент сам меняет данные во внешних системах | Запись (Битрикс24, 1С, почта, Telegram, вебхук) агент только предлагает; выполняет человек кнопкой или по визе; перед выполнением — политика выхода данных по уровню доверия системы | `integrations/service.py` |
| Утечка данных 1С в облачную модель | У системы есть гриф данных; чтение отдаёт данные только в задачу с грифом не ниже (а такие идут на локальных моделях); объекты 1С — белым списком, ключи — только GUID, строки фильтра экранируются | `integrations/service.py`, `connectors/onec.py` |
| Письмо или сообщение «не туда» | Почта — только на разрешённые домены, Telegram — только в разрешённые чаты; проверка и в демо-режиме | `connectors/messaging.py` |
| Подделка или повтор входящего события | HMAC-SHA256 от «время.тело» с допуском 5 минут, повтор того же события отклоняется (или токен Битрикс24 + список сетей отправителя); секрет показывается один раз; лимит событий в минуту; событие для модели — данные; задача — от имени настроившего (не шире его прав) и без выхода в интернет | `api/integrations.py`, `connectors/webhooks.py` |
| Вывод данных через интернет-инструмент агента | В задачах с грифом «Конфиденциально» и выше и в задачах из вебхуков чтение сайтов отключено (адрес запроса — тоже канал утечки) | `orchestration/engine.py` |
| Задача из протокола с выдуманными людьми и сроками | Факты — только правилами по справочнику; не найдено — «не определено» и блокировка; подтверждается отпечаток существенных полей; перед отправкой — повторная проверка | `processes/protocols/` |
| Компрометация мастер-ключа | `python -m orchestra rotate-master-key`: все секреты перешифровываются одной транзакцией, новый ключ подменяет старый только после фиксации | `core/rotate.py` |
| Угон сессии, CSRF | Случайный токен в HttpOnly + SameSite=Strict; под HTTPS — префикс `__Host-` (только этот хост, Secure, без поддоменов); в БД — только хеш; CSRF двойной отправкой; проверка Origin; простой 12 ч, предел 7 дней | `iam/deps.py`, `app.py` |
| Украденной сессией меняют права или ключи | Опасные действия (матрица прав, роли и пароли людей, владельцы, ключи моделей и интеграций, политика, канал тревог, выдача роли по запросу) — только если пароль (и код 2FA) вводили не дольше 10 минут назад; интерфейс спрашивает пароль сам и повторяет действие | `iam/deps.py` (`sudo`, `fresh`), `pages/Security.tsx` |
| DNS-rebinding (чужой сайт «превращается» в 127.0.0.1 и обращается к лаунчеру) | Проверка заголовка Host: только 127.0.0.1/localhost, домен из `ORCHESTRA_PUBLIC_URL` и `ORCHESTRA_ALLOWED_HOSTS`; остальное — 421 | `app.py`, `settings.py` |
| Доступ из интернета к внутреннему серверу | `ORCHESTRA_ALLOWED_NETWORKS` — только сети офиса и VPN; вебхукам — свой список `ORCHESTRA_HOOK_NETWORKS`; общий предел запросов с адреса; задаётся только конфигурацией сервера — захваченная учётка администратора не откроет систему наружу | `app.py` |
| XSS, кликджекинг | CSP без inline-скриптов, React экранирует вывод, `frame-ancestors 'none'`, `nosniff` | `app.py` |
| Эскалация через администрирование | Выдать право или роль — только в пределах своих прав и именно в том подразделении, где назначается роль; снятие запрета (deny) считается расширением; перенос подразделения, который дарит права, — только владельцу; управлять учётной записью (пароль, 2FA, роли, сессии) можно, только если все её управляющие и рискованные права есть и у тебя; свои роли меняет другой администратор; владельца меняет только владелец, смена владельцев — тревога | `iam/guard.py`, `api/iam.py` |
| «Дайте мне доступ» в обход правил | Запрос роли на срок (до 90 дней) из «Одобрений»; визирует только тот, у кого есть право назначать роли и все права этой роли в подразделении; свой запрос не одобрить; состав роли перепроверяется в момент визы; роль сама перестаёт действовать | `iam/requests.py` |
| Одобрил сам себе | Свой запрос не одобрить никому, включая владельца; визирующая роль задаётся в матрице | `approvals/service.py` |
| Подделка журнала задним числом | Хеш-цепочка; правка и удаление запрещены триггерами (PostgreSQL и SQLite); конец журнала после каждой записи заверяется подписью (ключ из мастер-ключа) в файле вне базы — обрезка хвоста и откат базы к старой копии видны при проверке; законное восстановление — `python -m orchestra reanchor` (само попадает в журнал) | `audit/`, миграции 0001, 0005 |
| SSRF и DNS-rebinding | Все исходящие клиенты (модели, интеграции, чтение сайтов, SDK Claude) идут через сетевой слой, который разрешает имя один раз, проверяет адрес и подключается ровно к нему (TLS — по исходному имени): агенту — только интернет, моделям и интеграциям — сеть компании без служебных адресов; у агента — ещё белый список доменов, редиректы с повторной проверкой, лимит размера | `core/netguard.py`, `tools/builtin.py` |

| Захват свежей установки | Первичная настройка только с разовым токеном; лаунчер передаёт его во фрагменте адреса (`#token=`) — он не уходит на сервер и в журналы; лаунчер слушает только 127.0.0.1 | `api/auth.py`, `launcher/` |

## Данные

- Хранятся: учётные записи (хеши паролей), задачи и результаты, версии промтов, визы, аудит, учёт вызовов моделей.
- Ключи моделей — только шифротекст. Мастер-ключ: `ORCHESTRA_MASTER_KEY` / `ORCHESTRA_MASTER_KEY_FILE` (сервер) или `data/master.key` под DPAPI (лаунчер).
- Сделайте резервную копию мастер-ключа отдельно от бэкапа БД.

## Периметр сервера

Задаётся в `deploy/.env` — только конфигурацией сервера, не из интерфейса:

```env
ORCHESTRA_ALLOWED_NETWORKS=10.0.0.0/8,192.168.0.0/16   # офис и VPN; остальным — 403
ORCHESTRA_HOOK_NETWORKS=                               # откуда принимать вебхуки (пусто — откуда угодно, они подписаны)
ORCHESTRA_ALLOWED_HOSTS=                               # доп. имена сервера, если открываете не по ORCHESTRA_DOMAIN
```

Можно отсечь чужие сети ещё на Caddy — см. закомментированный блок в `deploy/Caddyfile`.
Порядок проверки запроса: размер тела → Host → сеть → общий предел с адреса → сессия → CSRF → право → свежесть пароля (для опасных действий) → аудит.

## Резервные копии

- Сервер: `pg_dump` (см. `deploy/README.md`) + отдельно `secrets/master_key`. После восстановления базы — `python -m orchestra reanchor`.
- Лаунчер: `python -m orchestra backup D:\копии\orchestra.orchbak` — снимок базы, зашифрованный паролем копии (AES-256-GCM, scrypt);
  восстановление — `python -m orchestra restore …` при закрытом приложении (прежняя база сохраняется рядом, метка журнала переподписывается).
- Мастер-ключ храните отдельно от копий базы: без него секреты внутри копии не расшифровать, с ним — не держите вместе.
- Диск с данными — под BitLocker / LUKS: база знаний и задачи хранятся в базе открытым текстом.

## Эксплуатация

- Сервер компании — только за HTTPS (`deploy/`): приложение и БД во внутренней сети Docker, контейнер без root, read-only, без capabilities.
- Регулярно: `python -m orchestra verify-audit`; «Защита → Центр безопасности»: красные пункты состояния, неудачные попытки, незнакомые сессии.
- Канал тревог: подключите Telegram-бота или почту в «Интеграциях» и выберите его в центре безопасности.
- Сотрудник просит доступ — «Одобрения → Мои запросы → Запросить доступ»; на время замещения — временная роль в «Доступах → Люди».
- Подозрение на утечку мастер-ключа: остановить сервер → `python -m orchestra rotate-master-key` → обновить секрет → запустить
  (перешифровываются ключи моделей, секреты интеграций и 2FA; метка журнала переподписывается).
- Владелец потерял пароль или телефон с 2FA: `python -m orchestra recover LOGIN --reset-2fa` в консоли сервера.
- Потерян телефон со вторым фактором: «Доступы → Люди → Безопасность → Сбросить 2FA» (в аудите).
- Политика выхода данных — «Модели → Маршруты и данные»; меняет только роль с `system.settings`.

## Чего пока нет (честно)

- Вход через корпоративный каталог (AD/LDAP, OIDC) — следующий этап; второй фактор уже есть.
- Лимиты по отделам и в рублях — сейчас лимиты в токенах на человека и на модель.
- Маскирование ПДн — регулярными выражениями; DLP-классификатор документов — в планах.
- Сканы без текстового слоя в базу знаний не принимаются (нужно распознавание).
- Ключи доступа (WebAuthn / passkeys) как второй фактор устойчивее TOTP к фишингу — в планах.
- Шифрование документов базы знаний на уровне записей — сейчас данные защищает шифрование диска.
- Отправка меток конца журнала во внешний SIEM/syslog — метка пока хранится в файле рядом с приложением.
- Внешний пентест — до выхода на всех сотрудников.
